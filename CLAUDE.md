# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Rails app for running Secret Santa groups: users sign up, create or join groups via a join code, add gift ideas, and the group owner assigns secret santa partners. Deployed to Fly.io (`fly.toml`, `Dockerfile`) automatically on push to `main` once lint and tests pass.

The stack is deliberately self-contained: SQLite only. Dev/test use a single database at `db/<env>/data.sqlite3`. Production uses four SQLite databases on the Fly volume at `/data` (primary plus Solid Cache, Solid Queue and Solid Cable, each with its own `db/*_schema.rb`); Solid Queue runs inside Puma via `SOLID_QUEUE_IN_PUMA`. Frontend uses importmap + Stimulus + Turbo for JS (no JS build step), and `tailwindcss-rails` for CSS. Ruby and Bun versions are pinned in `.tool-versions` (installed with mise: `mise install`); Bun is only for dev tooling (Prettier, oxlint and herb-lint, pinned exactly in `package.json`).

## Commands

```bash
bin/setup                                  # install gems and JS packages (bun), prepare DB
bin/dev                                    # Rails server (port 3000) + Tailwind watcher (Procfile.dev)
bin/rspec                                  # all tests
bin/rspec spec/models/join_group_spec.rb   # one file
bin/rspec spec/models/join_group_spec.rb:12 # one example
bundle exec standardrb                     # Ruby lint (use --fix to autocorrect), plus custom cops
bun run lint                               # Prettier + oxlint (JS, `.oxlintrc.json`) + herb-lint (ERB templates; `bun x herb-lint --fix`)
bundle exec herb analyze .                 # parse/compile every template ("herb validate")
bundle exec herb actionview check .        # every render call resolves to a partial
```

CI (`.github/workflows/test.yml`) runs `RAILS_ENV=test bin/rails assets:precompile` before specs — feature specs need compiled Tailwind assets, so run that (or have `bin/dev` running) if styles/assets are missing in tests.

Lefthook pre-commit runs prettier, standardrb `--fix`, oxlint `--fix` and herb-lint `--fix` on staged files, plus the two herb checks when templates change; CI runs all of them. Herb is configured in `.herb.yml`: every offense fails (down to info), and every view declares strict locals on its first line (`<%# locals: (...) %>`, `<%# locals: () %>` for none). It doesn't run the specs, so run `bin/rspec` before committing.

## Architecture

- **Authentication** (`app/controllers/concerns/authentication.rb`): hand-rolled and passwordless, and signing in and signing up are the same step. The sign-in page (the root URL) emails a magic link whether or not an account exists: an existing user gets `SessionMailer#sign_in_link` (token from `User.generates_token_for :sign_in`, 15 minutes, single-use because it embeds `last_signed_in_at`, which `User#record_sign_in` bumps); an unknown email gets `#sign_up_link`, whose token is the signed email (`User.generate_sign_up_token`), and the account is only created when that link is followed (single-use because it's rejected once the email has an account). The response is the same "check your email" page either way. The link is `GET /session/magic_link?token=…` (`MagicLinksController`); GET only shows a confirmation that submits itself; the POST sets the encrypted `user_id` cookie so email scanners/prefetchers can't burn the token. New accounts have no `name` (the column is nullable); `require_logged_in` sends them to `DisplayNamesController` ("What should we call you?") before anything else. `session[:join_code]` is baked into the link as `join_code=…` at send time (the link may open in another browser), and a join code leads to the join page after sign-in (after the display name step for new accounts). Controllers opt in to protection with `before_action :require_logged_in`.
- **`Current`** (`app/models/current.rb`): `CurrentAttributes` holding `user` and `group`. Setting `Current.user` also sets `Current.group` to the user's last group — the app has an implicit "current group" concept that the dashboard and `User#ideas_in_current_group` depend on. A chosen group (`select_group`, e.g. via `dashboard_path(group_id:)` from the account page, or after creating/joining) is kept in `session[:group_id]` and overrides that default.
- **Domain models**: `User` ↔ `Group` through `UserGroup` (membership); `Group#owner` is a `User`; `Pair` (user → other, scoped to a group) is the secret santa assignment, generated by `Group#assign_partners` (needs >2 members; reshuffles until no self-pairings); `Idea` belongs to a user and group.
- **Action/form objects in `app/models/`**: multi-step operations live in plain `ActiveModel` classes rather than controllers — e.g. `JoinGroup` (`save`) and `RemoveGroupMembership` (`perform`, clears pairs when membership changes). Follow this pattern for new non-trivial operations.
- **Controllers** pass data to views via `render locals: {...}` rather than instance variables, and read params with `params.expect(key: [...])`, never `require(...).permit(...)` (enforced by the custom `SecretSanta/ParamsExpect` cop).
- **Custom RuboCop cops** live in `lib/rubocop/cop/secret_santa/` (ignored by Rails autoloading), are specced in `spec/lib/rubocop/cop/`, and are loaded alongside Standard's rules through `extend_config` in `.standard.yml` → `.standard_ext.yml`. There are no flash messages: the page a request lands on should make the outcome obvious (the pending-email box, the group gone from the list, …). Problems that can't be shown that way get a page of their own (`shared/message`, e.g. an expired link) or an inline error on the form (e.g. rate limits). People without a group are sent from the dashboard to the join page.
- **Rate limiting**: `rate_limit` on `SessionsController#create` (per IP and per email); counters live in `Rails.cache`, so they are inert in dev's `:null_store` (test uses `:memory_store`, cleared before each example).
- **Organiser tools** live on the dashboard: draw/redraw names (`PATCH /groups/:id` with `assign_partners`/`reassign_partners`), add/remove rules (`GroupRulesController`), remove members, and "Reset for this year" (`POST /groups/:group_id/reset`, `GroupResetsController` → `Group#reset`, which clears pairings and ideas but keeps members and rules). Renaming is the "Group name" card near the bottom (`PATCH /groups/:id`), not on the title, which is the group switcher. Creating a group lands on `groups#created` (join code + invite buttons).
- **Join flow** (`JoinController`): `/join/:join_code` links work for logged-out users by stashing the code in the session and picking it back up after sign-in and the display name step. With a code it shows a "You're invited" confirmation; without one, a code entry form.
- **Icons**: `IconComponent` (`app/components/`, ViewComponent) inlines Heroicons (24px outline) from `app/assets/images/icons/<name>.svg`; use the `icon(:name, size:, class:, aria:)` helper. Icons are `aria-hidden` unless given an `aria-label`, so the surrounding button/link supplies the accessible name. Sources hold only drawing attributes (`spec/assets/icons_spec.rb` enforces it), so strip `aria-hidden`/`data-slot` when adding a Heroicon. No emoji in the UI.
- **Group rules** are plain text, one `Rule` row per rule (`Group#rules`, in the order added). The create-group form builds the list client-side (`rule_list_controller.js`) and submits `group[rule_texts][]`.
- **Confirmations**: `data-turbo-confirm` opens a styled `<dialog>` (`shared/_confirm_dialog`, `confirm_dialog_controller.js`, which replaces `Turbo.config.forms.confirm`). Add `data-confirm-button` for the confirm label and `data-confirm-details` pointing at a `shared/_confirm_details` template for the icon and consequences list. In feature specs use `confirm_dialog("Yes, …")`, not `accept_confirm`.
- **Account page** (`users#edit`): separate name and email forms (`UpdateAccount` leaves an unsubmitted field alone), pending-email resend/cancel, sign out, the user's groups (with Leave, the only place members leave a group) in the right-hand column on desktop, and account deletion via `DeleteAccount` (deletes groups they organise). The header has no menu: the logo goes to the dashboard and the Account button to this page.
- **Layouts**: everything before the dashboard (sign in, check email, magic link, display name, join, start a group, group created) uses `layouts/getting_started`: no header, and a centred icon tile, title and subtitle set with `content_for :icon/:title/:subtitle`. Only the dashboard and account pages use `application` with the header. The privacy policy and terms (`LegalPagesController`, `/privacy` and `/terms`, linked from the sign-in page's footer) use `layouts/document`, readable signed in or out. All three layouts share `layouts/_head`.
- **Dashboard layout**: one column on phones; from `lg` a two-column grid with gift ideas on the right. Pages opt into the wider container with `content_for :wide`. Members of several groups get a group switcher on the title (`dashboards/_group_switcher`, a `<details>` closed by `menu_controller.js`).
- **Email changes** (`UpdateAccount`, `EmailConfirmationsController`): the account form saves the name directly, but a new email is held in `users.unconfirmed_email` and a link (`generates_token_for :email_change`, 1 hour, tied to the pending address) is mailed to it by `UserMailer`. The GET landing auto-submits a POST that calls `User#confirm_email_change`; works signed out. Only email-changing submits count toward the `update` rate limit.
- **Forms**: `FormBuilders::TailwindFormBuilder` (`app/lib/form_builders/`) is set as the global default form builder in `ApplicationHelper` and applies Tailwind classes to fields.
- **Mail**: Action Mailer sends directly over SMTP (no mail service gem); production uses Resend's SMTP server (`smtp.resend.com`, username `resend`, an API key as the password) with the verified sending domain `updates.secretsanta.getmuddle.app`. Env vars: `SMTP_ADDRESS`, `SMTP_PORT` (default 587), `SMTP_DOMAIN`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `MAILER_FROM` (defaults to `santa@updates.secretsanta.getmuddle.app`), `APP_HOST` (link host, defaults to `secretsanta.getmuddle.app`). `CONTACT_EMAIL` is the address on the privacy policy and terms (defaults to the `MAILER_FROM` address). The privacy policy and terms name Fly.io and Resend as the services handling user data, so update them if either changes. In dev without `SMTP_ADDRESS`, mail uses the `:test` method. Either way, dev mail is printed decoded to the log by the `DevelopmentMailLogger` observer (`lib/development_mail_logger.rb`), so follow the sign-in link from the `bin/dev` output. Production sends via `deliver_later` on Solid Queue; the test env uses the `:inline` queue adapter so mail lands in `ActionMailer::Base.deliveries`. Mailer previews live in `spec/mailers/previews`.

## Testing

- RSpec with FactoryBot (`spec/factories`), Capybara + Cuprite (headless Chrome) for feature specs; Cuprite is the default driver for all feature specs.
- Fast sign-in for tests: `Middleware::Test::Authentication` (`lib/middleware/test/authentication.rb`, mounted only in the test env) exposes a path that sets the auth cookie. Use `authenticate(user)` in feature and request specs (`spec/support/helpers/authentication_helper.rb`); `sign_in(user)` (feature specs) drives the real flow instead: request a link from the sign-in page (`request_magic_link(email)`), read the URL from the last delivered email (`last_magic_link_url`), visit it (the page signs in by itself via JS). `follow_magic_link` does the last two steps.
- Request specs live under `spec/requests/` organised by resource path; model specs cover the action objects.
